# 项目笔记

结构说明、命令、校验规则表见 `README.md`。本文件只记不在别处的上下文：
项目定位、当初的设计取舍、以及做这个库时遇到的判断。

## 在方法论里的位置

PXAI 四层推演链路：本体 → 知识库 → 经营模型 → 仿真引擎。
半导体是继蓝莓种植、规模化养猪、大闸蟹养殖、玻璃制造、儿童健康之后的第 6 个行业。

四层现已形成一个最小可执行闭环。第三层使用独立 YAML 经营模型引用本体 ID，第四层以确定性场景对比运行干预；本体上的 `economic_hooks` 仍只负责定性传导，不承载未经验证的弹性系数。当前实现用于证明链路和暴露数据缺口，不等同于现场数字孪生。

## 四个设计决定

1. **本体从零构建**，不基于已有行业项目扩建。跨行业复用走 `analogous_to` 显式映射，
   而不是继承一份公共本体——后者会把别的行业的建模包袱带进来。
2. **知识库落地形态先简单**。当前就是一层 kb 实例（异常处置 Playbook），
   先看效果，复杂形态后续再探索。
3. **无内部数据接口**。知识来自模型预训练知识、跨行业类比、公网公开资料三处，
   `provenance` 如实标注区分。
4. **自动改本体是可选项**。`config.yaml` 的 `review` 段支持人工审核与全自动两种模式，
   分级依据是回退成本。
5. **单执行体**。所有流程（选题 → 取材 → 建模 → changeset → 自审 → 合并 → 验证）
   由当前 Agent 顺序做完，不派 SubAgent；确定性检查交给 `precheck.py` 与
   `validate.py`，判断部分自审并在 verdict 里标 `self:*`。

## 建这个库时的几个判断

**为什么坚持"主流程 + 风险图谱"两部分都要。**
只有主流程，本体就只是工艺流程图，无法支撑排查；只有风险图谱，
异常就失去发生位置的上下文，无法判断影响范围与传播方向。
这个组合是跨行业可复用的部分，换到养猪或玻璃制造，骨架不变。

**为什么派生关系不手写。** `belongs_to`/`controls`/`measured_by`/`performed_on`
已经隐含在实体的 `stage`/`parameters`/`metrics`/`materials`/`equipment` 字段里。
再在关系文件里写一遍，就是同一事实两处维护，必然漂移。
由 `common.py` 在加载时展开，只有一个录入点。

**关系端点类型报错通常是建模错误，不是校验太严。**
建库过程中撞过三次，每次都是建模问题：`Hold blocks` 的对象应该是 Route 而不是队列 State；
`refines`/`analogous_to` 的 from/to 少列了 `RiskNode`。
正确的反应是改建模，不是放宽 meta-schema 去迁就。

**但收紧约束之前要先看实际数据，别照着文档写。**
给 `cause_ref` 补类型约束时，kb_schema 的描述只写了 Cause / Parameter / Process 三种，
按描述实现会判错一批正当条目：实际还用到 Anomaly（异常级联）和 State（Hold 造成堆积），
而 `may_cause` 关系的 `from` 端本来就允许这五种。
错的是 schema 描述写窄了，不是数据。所以改的是描述，不是数据。

**契约文档和脚本不一致时，退出码 0 也可能什么都没干。**
顶层键写成 `meta:` / `target:` 而脚本读 `changeset:` / `target_file:` 时，
`apply_changeset.py` 打印一行跳过继续、不报错，结论是
"自动放行 0 条 | 待人工审核 0 条"、退出码 0。定时任务只看退出码会一直
以为在正常更新。契约文档已对齐脚本，并写明这个静默失败模式与它的信号
（裁决输出里 `标题：None`）。**脚本才是真源，文档要拿实跑对齐。**

**取材工具是流水线而不是备选项，而"更强"的工具在 PDF 上最弱。**
直觉上 playwright 起真实浏览器，应该能力最强、能覆盖 WebFetch。实测反了：
PDF 上 playwright 是三者里最差的——Chrome 的阅读器渲染得出来，
但不向 accessibility tree 暴露任何文本，快照 0 字节，
连正文关键词都搜不到；WebFetch 至少把文件落到磁盘，让本地 PyMuPDF 能解。
反过来 `jedec.org` 的标准页对 WebFetch 返 403，playwright 正常取到。
三个工具没有强弱关系，只有各自的独占能力：WebSearch 独占"发现地址"，
playwright 独占"绕过反爬"，PyMuPDF 独占"读出 PDF 里的数值"。
按能力分工，不按"哪个更强"选。

**溯源最容易错的不是 URL 填没填，是归属填对没填对。**
校验器只能查 `ref` 字段存在，查不了归属正确。两个典型形态：
MSL floor life 表出自 J-STD-033（管搬运储存），不是检索时常用的
J-STD-020（管回流焊峰值温度 Tc），两者常被混引；
而 `jedec.org/.../j-std-033c` 这个地址实际服务的是 J-STD-033D，
`033d` 路径反而 404。两处都能通过校验，都是错的溯源。
所以归属要以取到的文档原文怎么说为准，不按自己的检索关键词归因；
URL 与版本号不一致时把差异写进 `notes`，否则后来的人会以为记错了。

**文档不写能从脚本读出来的数。**
同一事实存在多份副本必然漂移，而数字漂了和规则号漂了一样——不报错，
只是悄悄变错。写死的记录数在合并一条 kb 实例后就成了错的。

判据是"这个数字有没有脚本能算出来"：能算的一律不写，改成写清怎么算。
剩下真正该由人记的是脚本读不出来的东西——为什么这么建、哪里是有意简化、
踩过什么坑。这类内容不随实体数变化，也就不需要跟着更新。

副产品是维护成本从"每次改本体都要扫一遍文档"降到零。
更新本体和知识库以后只需要跑 `validate.py` 和 `build_index.py`，
不必再回头翻 md 找哪里写了数字。

**零 warn 需要被怀疑。** 跑出 0 error / 0 warn 时要用故障注入验一遍：
注入孤立实体和断裂的 Route.steps，看对应的 warn 是否真的报。
一个从不报错的校验器和没有校验器是等价的。

**提案内依赖要在裁决时就连锁转人工，而不是靠合并失败回滚。**
让 kb_case 先合并、撞上引用的实体还没落库，回滚机制虽然能兜住，
但让可预见的失败发生一次再兜底是浪费。
现在 `apply_changeset.py` 在裁决阶段就检查提案内依赖。

**声明了但零实例的类型，比没声明更糟。** 校验没有规则要求每个类型都得有
实例，所以这种类型可以安静地存在很久：读 meta-schema 的人以为这个视角
已经建好了，查图的人一条实例都搜不到。形态和数字漂移、规则号漂移是同一类
——**声明与事实分离，而分离不产生任何信号**。
一个能随意改的 schema 声明本身就是它没被用过的证据。

**设备不是工序的属性，是产能的载体。** 设备不建成实体时，"曝光是瓶颈"
这句话只能写在 `fab.process.photo_exposure` 的 description 里当文字。
建成独立实体后 Scanner 可以挂自己的 `economic_hooks`
（`capacity_commit / equipment_oee / cost_per_unit / throughput`），
也可以承载"批式 vs 单片式""换型时间""专机专用"这类
**属于机台而不属于工序**的事实——扩散炉的凑批矛盾、植入机的
setup time 依赖前后批次组合、塑封机的模具专用性，这些都是排程和
产能问题的真正约束来源，挂在工序上会串味。

用 `tags` 记 `batch / single_wafer / single_unit / bottleneck` 而不是
新增字段，是为了避免为三个枚举值动 schema。代价是这些标签校验不到
取值范围（R011 只管 `economic_hooks.affects`），等真要用来算产能时再收紧。

**"不全面"不是缺陷,"边界不可见"才是。** 这个库是按问题域建的,证据很硬:
风险图谱边明显多于流程骨架边,知识库实例全部通过 `anomaly_ref` 锚在异常上,
而且 `kb_schema` 只有一种形状(症状/根因/检出/处置/影响)——它不是"能装各种知识的库",
是异常排查 Playbook 库,连装别的东西的字段都没有。

按问题域建本身是本体工程的标准做法,追求全面才是已知的失败模式:
想做通用上层本体的(Cyc、SUMO)基本没落地,成功的(Gene Ontology、SNOMED)
全是死死卡住一个域。原因很实际——全面没有终点,不存在"建完了"的状态,
而卡住问题域可以判断够不够。

所以补的不是覆盖面,是**把边界从建库者的判断里搬进文件**。
`competency-questions.yaml` 的 `in_scope` 是承诺,`out_of_scope` 是拒绝
(条数不写在这里,跑 `ask.py` 或直接读文件——写死了就会漂,这个坑本项目已经踩过)。
关键设计是 `requires` 声明依赖的类型与关系,让 R016 能查——只写问句就还是散文,
会和之前那些数字一样漂。

粒度停在类型和关系,不到具体实体 ID:到 ID 会让清单跟着每次增删动,
又多一个必须同步维护的地方,正是之前踩过的坑。

**R016 查得了依赖有没有实例,查不了遍历路径真不真通。** 典型形态:
一条"某台机台停机会波及哪些异常"的条目,依赖(Equipment / Process /
Anomaly / belongs_to / detected_at)全部有实例、R016 放行,而手工验时
只有一部分设备走得通。

原因不是数据缺失,是问句和路径配错:两跳走的是 `detected_at`,
而 `detected_at` 是**检出点**——异常在量测站被检出(CD 量测、缺陷扫描、AOI、终测),
只覆盖量测与测试工序是语义正确的,不是漏建。扩散炉停机不会"在扩散炉被检出"。

所以新增 in_scope 条目必须手工走一遍 `answered_via`,不能只看 R016 放行。
校验能挡结构性失效,挡不了语义性空承诺。

相关的一条真断裂记为 OOS11:**"哪台机停了"和"停机异常"是两套互不连接的
表达。** `fab.anomaly.scanner_down` 存在且 refines 到
`core.anomaly.equipment_down`,但它和设备实体之间没有任何边。

`out_of_scope` 那条"不要用模型知识硬编答案"是这份清单最实的价值。
库外知识伪装成库内知识,溯源链断掉而且没人知道断了——比答不出来坏得多,
因为答不出来会促使人去补,答错了不会。

**清单只有可执行才算约束。** 写完 YAML 之后判定还落在"读清单的人怎么想"上,
跟没写差别不大——所以有了 `ask.py`:问题进去,退出码出来(0/2/3),
`--probe` 还能沿边走一遍。三层里第三层才是关键,它挡的正好是 R016 挡不住的
语义性空承诺,把手工验的动作变成一条命令。

调这个脚本时两条经验:

- **整词匹配太脆。** "CD 超规在哪道工序**检出**"配不上意图词"哪道工序**发现**"。
  加了 bigram 部分命中兜底(重叠率 ≥0.5 记半分),不引 jieba——中文分词
  换一个依赖不值得,字符 bigram 在这个量级够用。
- **同分时 `out_of_scope` 必须优先。** "扩散炉停机会引发什么异常"会因
  "会引发"这类意图词命中 in_scope 条目而被误判可答,而它该落 OOS11。错拒的代价是多查一次,
  错答的代价是信任,两边不对称。同时判成 `2` 时把次高的 in_scope 候选作为
  "相近的可答问题"打出来——多数越界只是措辞问题,死拒不如给改写方向。

匹配层是手写意图词,这是有意的:实体名从本体自动派生(不用维护),
但"用户会怎么问"派生不出来。代价是新增 CQ 必须同时想清楚问法,
漏了就退出码 `3`——比错答安全,但要靠用的人回头补词。

## 已知缺口

- **深度优先于广度**：光刻/蚀刻/键合/塑封建得较细，多金属层互连、
  先进封装（2.5D/3D、TSV、Chiplet）只留了扩展位
- **参数区间是典型值**，来自公开资料与模型知识，不对应任何具体厂的实际配方
- **检索是关键词匹配**，未做向量化。当前规模够用，实体数上千后需引入语义检索
- **`ext.*` 类比目标只有 ID 与说明**，未真正打通其他行业的本体文件
- **`human` 来源零出现**，全库无人工录入条目。`web` 来源已走过真实数据，
  R006 那条 web-必须带-URL 的分支不再是只在故障注入时验证过
- **跨行业类比只有一端**。`ext.*` 目标豁免本地解析，所以 `analogous_to` 现在
  写得对不对无法校验，只能靠人读。等第二个行业的本体落库，这条才能真正闭环
- **`economic_hooks` 是定性传导，不是量化模型**。有 `affects` 和 `note`，
  没有弹性系数、单位成本、周期时间数值。能答"传导到哪"，答不出"传导多少"
- **经营模型与仿真引擎已有最小闭环**。`business/` 放带单位、来源和本体引用的输入及受限算术公式；`simulation/scenarios/` 放 `set` / `multiply` / `add` 干预；`scripts/simulate.py` 输出 baseline、intervention、delta、回收期和证据等级。当前示例是植球治具堵塞→缺球率→经营贡献，输入是演示假设，不能替代现场数据
- **仿真仍是单周期确定性计算**。尚未建模 WIP 排队、设备换型、随机故障、批次流动、产能瓶颈和蒙特卡洛置信区间
- **设备只到机台粒度**。多腔体机台（蚀刻机、PVD/CVD）的实际调度单元是腔体，
  同机不同腔需分开做 SPC，现在建不出来。设备也没有产能字段（UPH、并测数、
  换型时间），这些事实目前只写在 description 的文字里
- **组织与供应链两个视角完全没有**。班别、操作员、治具、来料批次、
  客户端失效都不是实体。`ap.anomaly.delamination` 的 note 提了
  "漏出至客户端的代价"，但"客户"在本体里不存在。
  其中**岗位级建模是最便宜的一块**（记为 OOS12）：Action 实体全无 `owner_role`，
  kb 实例也无升级路径字段，所以"做什么"建了、"谁做"没建。补一个字段就能答，
  不需要人员级数据——这是当前性价比最高的一个缺口
- **`ask.py` 的意图词是手写的**。实体名从本体自动派生，问法派生不出来。
  漏词的表现是退出码 `3`（"清单里没有这个问题"）——安全但不准，要靠用的人回头补。
  跑一轮多样问法回归能把大部分漏词打出来，建议每次改 CQ 后跑一遍
